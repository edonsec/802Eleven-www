# demo/ — standalone UI sandbox

Mechanically extracted from `src/WebPage.cpp`'s `PAGE_HTML` PROGMEM literal by
`tools/extract_demo.py`. Represents the **full-feature build**
(`WITH_BLE=1 WITH_WIFI=1 WITH_SECURITYTOOLS=1`, i.e. `[env:802eleven]` +
`-D WITH_SECURITYTOOLS=1`, the `[env:esp32-s3-sec]` env) — every UI feature
live, no firmware attached. Runs by opening `demo/index.html` in a browser
(or `python -m http.server` from this dir).

## Files
- `index.html` — the HTML body, extracted verbatim (guard-flattened, see below).
- `style.css`  — the `<style>` block, extracted verbatim.
- `app.js`     — the `<script>` block, extracted verbatim.
- `mock-api.js` — **new, demo-only**. Installs a `window.fetch` override
  *before* `app.js` loads (load order matters: `app.js`'s own CSRF-echo IIFE
  wraps whatever `window.fetch` already is at parse time — see `index.html`'s
  `<script>` order). Fakes every `/api/*` route from `src/RadarServer.cpp`
  against an in-memory synthetic BLE/WiFi population that jitters/churns on a
  timer, so the dashboard feels alive without a device. **Not derived from
  WebPage.cpp — do not feed it through the reverse-translation skill.**
- `env-select.js` — **new, demo-only**. The "Env" header button — **self-injected**
  (`ensureButton()`, since `index.html` is regenerated by `tools/extract_demo.py`
  and would otherwise drop any hand-added markup) next to the gear icon — opens a popover to simulate board
  capabilities no single physical unit has all of at once: SD card present,
  dual-band radio, standalone dongle (no scout), GPS module, scout linked.
  Mutates `mock-api.js`'s `state` directly via `window.__mockState`.
  `capdual`/`dband`/`scoutLinked` already flow through `app.js`'s real
  `syncCapBand`/`syncScoutBand`/`.scout-only` gating, so those three are
  live-reactive; `sdBoard` is read on-demand by the Authorisations/Settings
  tabs (same as a real board's SD probe); `gps` gates `mock-api.js`'s
  per-AP `lat`/`lon` fabrication (see below) — a real dashboard consumer
  already exists for this (`app.js::showMacInfo`'s Location row, fed today
  by a GPS session-log import), so toggling this flag just makes the WiFi
  records carry those fields like a GPS-tagged capture would.
  **Not derived from WebPage.cpp — do not feed through the
  reverse-translation skill.**
- `view-select.js` — **new, demo-only**. The "View: Full/Mobile" header
  button — self-injected (`ensureButton()`, same pattern as
  `env-select.js`) next to the gear icon. "Mobile"
  loads the same page fresh inside a `390x844` `<iframe>` instead of
  CSS-transforming the existing DOM — an iframe has its own layout viewport,
  so `@media` breakpoints in `style.css` actually re-evaluate and the page
  reflows like a real phone; squeezing the top-level DOM into a scaled box
  would leave `window`/`matchMedia` reporting the desktop width and the
  layout would never reflow. The iframe is inserted as a normal block right
  after the real `<header>`, and every other top-level body child is
  `display:none`d rather than covered by a `position:fixed` overlay — so the
  header, and this toggle button living in it, stay in normal page flow and
  reachable in both modes (an earlier full-viewport-overlay version buried
  the header, and thus the button, the moment mobile mode was on). Guards
  against recursing into itself via a `?demoMobilePreview=1` marker on the
  iframe's own `src`, **not** a `window.self !== window.top` check — this
  page is itself loaded inside an iframe by the `sims/index.html` launcher,
  so that check is true even on a normal top-level open and would hide the
  button there too. State persisted in `localStorage`. **Not derived from
  WebPage.cpp — do not feed through the reverse-translation skill.**

## Regenerating after a WebPage.cpp edit
```
python tools/extract_demo.py
```
Overwrites `style.css` and `app.js` outright, and splices the fresh body into
`index.html` in place — it reads the existing `index.html`, keeps everything
outside `<body>...</body>` verbatim (favicon/stylesheet `<link>`, the trailing
`<script src="...">` tags for `view-select.js`/`mock-api.js`/
`env-select.js`/`app.js`), and replaces only the body content between them. So
`index.html`'s `<head>` and its script tags are themselves hand-maintained
(add a new one by editing `index.html` directly) — only the body is
mechanically overwritten.
**`mock-api.js`, `view-select.js`, `env-select.js`, and
this file are hand-written and never touched by the script.**

## The guard system (read this before writing the reverse skill)
`WebPage.cpp` wraps feature-specific chunks of the HTML/CSS/JS in C
preprocessor `#if WITH_BLE` / `#if WITH_WIFI` / `#if WITH_SECURITYTOOLS`
(and combinations/negations) so a single-radar or non-sec-tools firmware
build compiles a smaller page with that chrome absent. The extractor
evaluates every guard against `{WITH_BLE:1, WITH_WIFI:1,
WITH_SECURITYTOOLS:1}` (this demo's target build) and:

1. **Keeps** the content of whichever branch (`#if`/`#elif`/`#else`) evaluates
   true under those flags.
2. **Drops** content in branches that evaluate false — for this flag set,
   that's only two small blocks (both listed below); everything else in the
   file lit up.
3. Wraps every **kept** conditional block in a marker comment pair, in the
   comment syntax native to whichever file the block landed in:
   - HTML: `<!-- @GUARD:IF <cond> -->` … `<!-- @ENDGUARD -->`
   - CSS/JS: `/* @GUARD:IF <cond> */` … `/* @ENDGUARD */`
   - `@GUARD:ELIF <cond>` / `@GUARD:ELSE` mark content that came from an
     `#elif`/`#else` branch (rare in this file — only one spot, the BLE+WiFi
     import-mode branch in `app.js` around `const wifi = o.wifi && ...`).

   These markers are the reverse skill's map back to `#if`/`#endif` in
   `WebPage.cpp`: to re-embed an edited block, find its `@GUARD` pair, wrap
   the corresponding C++ chunk in `#if <cond>` / `#endif` (or
   `#elif`/`#else` as marked), and drop the marker comments themselves (they
   don't exist in the real file).

## Dropped branches (do NOT exist in this demo — reconstruct from `WebPage.cpp` directly if ever needed)
These are false under `WITH_BLE=1, WITH_WIFI=1` so the extractor discarded
them; they only matter for single-radar builds, which this demo doesn't
represent:
- `WebPage.cpp:511-516` — `#if !WITH_BLE` / `#if !WITH_WIFI` hard-hide CSS
  (`.ble-only{display:none!important}` / `.wifi-only{...}`) for whichever
  radar a single-radar build lacks.
- `WebPage.cpp:3326-3330` — `#if !WITH_BLE` → `syncModeUI('wifi')` /
  `#elif !WITH_WIFI` → `syncModeUI('ble')`, the boot-time mode lock for a
  single-radar build.

If a change ever needs one of those paths tested, edit `WebPage.cpp` and
flash a `esp32-s3-wifi-only` / `esp32-s3-ble-only` build instead (see
CLAUDE.md's "Feature-flag UI verify" note) — this demo intentionally only
covers the full/`sec` build.

## Translating demo edits back to WebPage.cpp
A separate skill will do this mechanically:
1. Diff `index.html`/`style.css`/`app.js` against the last-generated
   versions (or against a fresh `python tools/extract_demo.py` run) to find
   what changed.
2. For unguarded (no enclosing `@GUARD`) changes: apply the same text edit
   directly inside the matching `R"HTML(...)HTML"` chunk in `WebPage.cpp`.
3. For changes inside a `@GUARD` span: apply the edit inside that same
   `#if <cond>` (or `#elif`/`#else`) block in `WebPage.cpp` — the marker's
   `<cond>` is copy-pasteable.
4. Re-run the extractor and diff again — it should reproduce the edited demo
   exactly (modulo `mock-api.js`, which isn't derived from `WebPage.cpp` at
   all).
5. Rebuild (`pio run`) to make sure the edit compiles across every env,
   including the single-radar ones the demo doesn't cover.
